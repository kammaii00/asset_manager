# Plan: 코스피/코스닥 종목 심층분석

## 1. 개요 (Background & Motivation)

기존 자산관리 앱은 "내가 무엇을 얼마나 들고 있는가"를 보여주지만, "그것이 좋은 종목인가"는 답하지 못한다. 종목명을 입력하면 실제 재무제표·시세·수급·뉴스·거시지표를 수집해 심층 분석하고 투자 적합도를 리포트로 제시하는 기능을 추가한다.

**별도 앱이 아닌 기존 앱에 통합하는 이유:** 보유 종목 정보가 분석의 최고 입력값이기 때문이다. 독립 앱은 "삼성전자는 좋은 회사인가"까지만 답하지만, 통합하면 "반도체 비중이 이미 40%인 내 포트폴리오에 이 종목을 더 담는 것이 맞는가"를 답할 수 있다. 인증·배포·DB·디자인 인프라 재구축 비용도 불필요하다.

## 2. 설계 원칙 (Design Principles)

이 4가지가 결과물의 신뢰도를 결정한다.

1. **숫자는 코드가, 해석은 AI가.** LLM에게 재무비율을 계산시키면 반드시 틀린다. 모든 지표는 결정론적 코드로 계산하고, AI는 "이 숫자가 무엇을 의미하는가"만 판단한다.
2. **절대평가 금지, 동종업계 상대평가.** "PER 12배는 싸다"는 무의미하다. 모든 지표를 같은 업종 내 백분위(percentile)로 변환해 평가한다.
3. **모든 리포트는 시점 스냅샷(point-in-time).** 분석에 사용한 원본 데이터를 리포트와 함께 저장한다. 6개월 뒤 "그때 판단이 맞았나"를 검증할 수 없으면 시스템이 개선되지 않는다.
4. **결론은 매수/매도가 아니라 리스크-보상 프로파일.** 근거·확신도·반대 논거(bear case)를 함께 제시하고 최종 판단은 사용자에게 남긴다. 무인가 투자자문 규제 회피 측면에서도 이 구조가 안전하다.

## 3. 아키텍처 (Architecture)

### A. 실행 구조 — Cloud Functions v2 Task Queue

종목 1건 분석에 2~5분이 걸리므로 Next.js Route Handler에서 직접 처리할 수 없다. **Cloud Tasks 기반 큐 함수**로 분리한다.

```
[브라우저] /analysis 페이지
     │ POST
     ▼
[Next.js Route Handler] /api/analysis
     │ · 인증 검증 (getUserIdFromRequest)
     │ · users/{uid}/analysis_requests 문서 생성 (status: queued)
     │ · getFunctions().taskQueue('analyzeStock').enqueue()
     │ · 즉시 202 응답 (리포트를 기다리지 않음)
     ▼
[Cloud Functions v2] analyzeStock (onTaskDispatched)
     │ · 데이터 수집 → 정량 계산 → AI 분석 → 검증
     │ · 진행률을 Firestore에 실시간 기록
     ▼
[Firestore] stock_analyses / analysis_requests
     │ onSnapshot
     ▼
[브라우저] 진행률·결과 실시간 표시
```

**왜 Pub/Sub + Cloud Run Job이 아닌가:** 기존 프로젝트가 Cloud Functions v2(`onSchedule`)와 `defineSecret`만 사용 중이다. Pub/Sub·Cloud Run Job·별도 Dockerfile·별도 CI를 도입하면 관리 지점이 3개 늘어난다. Task Queue 함수는 기존 `functions/` 배포 파이프라인에 그대로 올라가면서 다음을 기본 제공한다.

- **`rateLimits`** — KIS 유량 제한(초당 20건) 대응을 큐 설정으로 해결
- **`retryConfig`** — 외부 API 일시 장애 시 자동 재시도
- **긴 타임아웃** — `timeoutSeconds: 540`(9분)으로 설정

### B. 언어 — Node.js (기존 `functions/`와 동일)

> ⚠️ **초기 논의에서 Python을 권고했으나 철회한다.** 코드를 확인한 결과 다음이 명확해졌다.
>
> - `functions/`는 이미 Node 22 ESM으로 구성돼 있고 배포·시크릿 관리가 검증돼 있다
> - Python을 쓰려면 pandas의 이점이 필요한데, **본 설계의 계산은 pandas가 필요한 수준이 아니다.** ROE·CAGR·백분위 순위는 순수 JS 수십 줄로 충분하다
> - 언어를 나누면 배포 파이프라인·시크릿 저장소·CI가 이중화된다
>
> 대규모 백테스트나 시계열 회귀가 필요해지는 시점(Phase 4 이후)에 별도 Python 서비스를 검토한다.

### C. 기존 기능 불간섭 원칙

- `web_app`은 **페이지 1개 + API 라우트 1개**만 추가한다. 기존 화면·스토어·빌드 설정을 건드리지 않는다.
- **Yahoo Finance 연동은 그대로 둔다.** 해외주식·코인·환율 자산 평가에 쓰이고 있다. KIS는 신규 워커에서 국내주식 전용으로만 사용한다.
- 워커가 실패해도 기존 자산관리 기능은 영향받지 않는다.

### DART 고유번호 함정

DART는 종목코드(`005930`)가 아니라 **8자리 고유번호(`corp_code`, 예 `00126380`)**로 조회한다. `corpCode.xml` API는 확장자가 `.xml`이지만 실제로는 **ZIP 파일**로 응답한다. 압축을 풀면 전체 법인의 `corp_code ↔ stock_code` 매핑이 나온다. 이 적재가 Phase 1의 첫 작업이다.

### KIS 접근토큰 함정

토큰은 24시간 유효하지만 **재발급은 1분에 1회로 제한**된다. 워커 실행마다 새로 발급받으면 즉시 차단된다.

→ Firestore `system/kis_token` 문서에 `access_token` + `expires_at`을 저장하고, 만료 10분 전에만 갱신한다. (`market_briefings`와 동일한 공용 문서 패턴)

### KIS 실측으로 확인한 제약 (2026-08-05)

실제 호출로 검증한 결과 설계에 반영해야 할 한계가 두 가지 있다.

| 항목 | 실측 결과 | 대응 |
|---|---|---|
| 일봉 1회 반환량 | 호출당 약 100건 상한 | 3년치(약 750 거래일)는 **구간을 나눠 8회 내외 반복 호출** 후 병합 |
| 투자자별 매매동향 | **최근 30 거래일만** 반환 | 수급 분석 구간을 60일 → **30일**로 조정 |
| 유량 제한 | 문서상 초당 20건이나 **300ms 간격에서도 초과 발생** | 호출 간격 300ms + **지수 백오프 재시도 3회**. 재시도 없이는 유량 오류를 '종목 없음'으로 오인한다 |
| 없는 종목코드 | 오류가 아니라 **모든 값이 0인 정상 응답**(rt_cd=0) | `상장주식수 > 0 && 현재가 > 0`으로 실존 여부를 별도 판정. 없으면 `tradable: false` |

**없는 종목코드 함정이 특히 중요하다.** DART 고유번호 파일 3,981건에는 상장폐지 이력 종목이 섞여 있는데, KIS가 오류를 주지 않으므로 검사를 넣지 않으면 **현재가 0원짜리 유령 종목이 정상 종목으로 저장된다**(실측: `999999`, `000000`).

**Red Flag 판정 필드 (전체 80개 필드를 덤프해 확인)**

| 필드 | 값 | 의미 |
|---|---|---|
| `mang_issu_cls_code` | `Y`/`N` | **관리종목 여부 — 이것이 정답 필드다** |
| `mrkt_warn_cls_code` | `00`/`01`/`02`/`03` | 없음 / 투자주의 / 투자경고 / 투자위험 |
| `iscd_stat_cls_code` | `55` 등 | 종목상태 분류값(정상 종목은 `55`). 보조 지표로만 사용 |
| `vi_cls_code` | `Y`/`N` | 변동성완화장치(VI) 발동 — 참고용 |

**시장구분은 `rprs_mrkt_kor_name`이지만 값이 시장명이 아니라 지수명이다.** 실측에서 삼성전자는 `KOSPI200`, 에코프로비엠은 `KSQ150`을 반환했다. 따라서 문자열 매핑이 필요하다.

```
/KSQ|KOSDAQ|코스닥/  → KOSDAQ  → Yahoo 심볼 접미사 .KQ
/KOSPI|KRX|유가/     → KOSPI   → Yahoo 심볼 접미사 .KS
그 외                 → UNKNOWN (로그를 남기고 수동 확인)
```

주요 필드: `stck_prpr`(현재가) `hts_avls`(시가총액, 억원) `lstn_stcn`(상장주식수) `per` `pbr` `eps` `bps` `w52_hgpr`/`w52_lwpr`(52주 고저) `hts_frgn_ehrt`(외국인보유비율) `bstp_kor_isnm`(업종명). 수급은 `frgn_ntby_qty`(외국인 순매수 수량) `orgn_ntby_qty`(기관) `prsn_ntby_qty`(개인)와 각각의 금액 버전(`_tr_pbmn`).

### KIS 보안 — 조회 전용 강제

KIS 앱키는 **실제 계좌의 주문 권한을 포함**한다. DART·ECOS 키와 위험도가 다르다.

1. 시크릿은 `defineSecret`으로만 주입 (`briefing.js`의 `GEMINI_API_KEY` 패턴)
2. **주문 엔드포인트를 코드에 작성하지 않는다.** `/uapi/domestic-stock/v1/trading/*` 경로가 존재하지 않으면 버그로도 주문이 나갈 수 없다
3. KIS 클라이언트에 **허용 경로 화이트리스트**를 두고 그 외 호출은 코드 레벨에서 차단한다

## 5. 분석 파이프라인 (Pipeline)

```
[0] 종목 식별
    "삼성전자" → 005930 / KOSPI / 반도체 / corp_code=00126380
    · stock_master에서 조회 (동의어·구 사명 포함)
    · 후보가 여럿이면 사용자에게 선택 요청

[1] 데이터 수집 (병렬, 캐시 우선)
    재무제표 5년 / 공시 30건 / 일봉 3년 / 수급 30거래일 / 뉴스 50건 / 거시지표
    · 재무제표는 분기당 1회만 변하므로 Firestore 캐싱 → 재분석 시 비용 0

[2] 정량 분석 ── 100% 코드, AI 미사용
    수익성  : ROE, ROIC, 영업이익률, 마진 추세
    성장성  : 매출·영업이익 3Y CAGR, 최근 4분기 YoY
    안정성  : 부채비율, 유동비율, 이자보상배율, 순현금
    현금흐름: 영업CF vs 순이익 괴리(이익의 질), FCF, CAPEX 부담
    밸류에이션: PER/PBR/EV-EBITDA/PSR + 자체 5년 밴드 내 위치
    수급    : 외국인·기관 순매수 누적, 외국인 보유비중 변화
    → 전 지표를 업종 내 백분위로 변환

[3] 정성 분석 (AI) ── 병렬 3건
    (a) 뉴스   : 재료 vs 노이즈 구분, 감성, 반복 이슈
    (b) 공시   : 주주가치 훼손/증대 이벤트, 감사의견·계속기업 리스크
    (c) 사업   : 사업보고서 → 사업모델, 해자, 경쟁구도, 매출 편중도

[4] 거시/섹터 컨텍스트 (AI)
    금리·환율·업황 사이클이 이 종목 이익에 주는 방향성

[5] 종합 판단 (AI, 구조화 출력)
    입력: 위 전체 (숫자는 이미 계산 완료 상태)
    출력: 5축 점수 + 투자 논거 + Bear Case + 확신도 + 모니터링 지표
    ※ 사용자 보유 자산을 함께 전달해 포트폴리오 맥락 반영

[6] 검증 (AI 심판)
    "리포트의 모든 숫자가 원본 데이터와 일치하는가?"
    불일치 시 해당 섹션 재생성 → 환각 차단의 마지막 방어선
```

## 6. 평가 모델 (Scoring)

| 축 | 가중치 | 핵심 질문 |
|---|---:|---|
| **Quality** 수익성 | 25% | 돈을 잘 버는 회사인가 (ROE, ROIC, 마진 안정성) |
| **Value** 밸류에이션 | 25% | 지금 가격이 합리적인가 (업종 대비 + 자체 밴드 대비) |
| **Growth** 성장성 | 20% | 계속 커지는가 (CAGR, 최근 가속/둔화) |
| **Safety** 재무안정성 | 15% | 망하지 않는가 (부채, 이자보상, 현금흐름의 질) |
| **Sentiment** 수급·심리 | 15% | 큰손이 사고 있는가 (외국인·기관 수급, 뉴스, 모멘텀) |

**초기안 대비 조정 2건:**
- Sentiment 10% → **15%**. KIS 도입으로 외국인·기관 실제 순매수를 확보했다. 국내 시장에서 수급은 단기 주가를 설명하는 가장 강한 변수 중 하나이므로 뉴스 감성 수준의 가중치는 과소평가다.
- Safety 20% → **15%**. 치명적 위험은 아래 Red Flag가 별도 게이트로 잡아내므로 점수에 다시 반영하면 이중 계상이 된다.

**등급:** 85+ 매우 우수 / 70+ 우수 / 55+ 보통 / 40+ 주의 / 40미만 위험

### 동종업계 백분위의 현실적 제약

설계 원칙 ②는 동종업계 상대평가지만, **요청받은 종목만 수집하는 방식(§7)에서는 초기에 비교군이 없다.** 전종목을 미리 수집하지 않기로 한 결정의 대가다. 단계적으로 접근한다.

| 단계 | 기준 | 비고 |
|---|---|---|
| 초기 | **자체 시계열 밴드** + 절대 기준 | 구현 완료 — "이 회사 과거 대비 비싼가"는 비교군 없이도 판단 가능 |
| 축적 후 | 같은 업종 분석 이력이 3건 이상 쌓이면 **업종 백분위 활성화** | 분석할 때마다 `stock_master`에 지표가 남으므로 시간이 지나면 자연히 해결된다 |

업종은 KIS `bstp_kor_isnm`으로 이미 저장되므로 별도 수집이 필요 없다.

### 재무 지표 계산에서 실측으로 확인한 사항 (2026-08-05)

**① 밸류에이션은 지배주주 기준이어야 한다.**
연결 당기순이익에는 자회사의 비지배주주 몫이 섞여 있다. 연결 전체로 계산하면 시장 통용치와 어긋난다.

| 종목 | 연결 전체 기준 PER | **지배주주 기준 PER** | KIS 제공값 |
|---|---|---|---|
| 에코프로비엠 | 108.63 | **252.71** | 252.36 ✅ |
| 카카오 | 32.63 | **34.38** | 34.37 ✅ |

**② 우선주가 있는 종목은 KIS 값과 어긋난다.**
우선주가 없는 두 종목은 오차 0%로 일치했으나 삼성전자는 13% 차이가 났다. KIS 시가총액(`hts_avls`)은 보통주만 계산하는 반면 EPS·BPS는 우선주를 포함한 전체 자본 기준이라 분자·분모가 어긋나기 때문으로 보인다.

→ **현재 시점 밸류에이션은 거래소 기준인 KIS 값을 우선**하고, 자체 계산은 과거 연도 밴드 산출과 교차검증에 쓴다. 괴리가 10%를 넘으면 `crossCheck.diverged` 플래그로 표시해 특수 요인을 의심하게 한다.

**③ 적자·자본잠식은 예외가 아니라 정상 상태다.**
적자 기업의 PER, 자본잠식 기업의 PBR은 숫자를 만들어도 의미가 없고 음수 PER은 "싸다"로 오독된다. 계산 불가 시 예외를 던지지 않고 `null`을 반환한다. 적자→흑자 전환도 성장률로 표현되지 않으므로 `turnedProfitable` 플래그로 따로 남긴다(실측: 에코프로비엠 2024 영업손실 → 2025 흑자).

**Red Flag (점수와 무관하게 최상단 경고)**
- 감사의견 비적정 / 계속기업 불확실성
- 자본잠식
- 관리종목·거래정지·투자경고 지정
- 영업활동 현금흐름 3년 연속 음수
- 최근 대규모 유상증자·전환사채 발행

## 7. Firestore 스키마

기존 `market_briefings` 패턴(공용 데이터는 Admin SDK로만 접근)을 그대로 따른다. **`firestore.rules` 수정이 불필요하다** — 기본 차단(whitelisting) 규칙 아래 두고 API 라우트가 Admin SDK로만 읽는다.

```
# 공용 (유저 무관, Admin SDK 전용)
/stock_master/{ticker}                      종목 기본정보, corp_code, 시장구분, 업종
/stock_master/{ticker}/financials/{period}  재무제표 캐시 (분기 1회만 변함)
/stock_master/{ticker}/prices/{year}        일봉 — 연도별 1문서에 배열로 (약 250건, 25KB)
/stock_master/{ticker}/flows/{year}         투자자별 수급 — 동일 구조
/stock_analyses/{ticker}/reports/{date}     분석 리포트 본문
/sector_stats/{sector}/{period}             업종 백분위 계산용 통계
/system/kis_token                           KIS 접근토큰 캐시

# 개인
/users/{uid}/analysis_requests/{id}         요청 이력, 진행상태, 결과 참조
```

재무제표와 리포트를 **공용에 두는 것이 핵심**이다. 같은 종목 재분석 시 수집을 건너뛰어 API 호출과 Claude 비용을 아낀다.

### 수집 원칙 — 요청받은 종목만, 요청받은 그때

이 기능은 **신규 종목 발굴 도구**이지 전종목 감시 시스템이 아니다. 정기 수집 스케줄러를 두지 않는다.

| 대상 | 수집 시점 | 규모 |
|---|---|---|
| 분석을 요청한 종목 | 요청받은 그때 3년치를 한 번에 | 요청당 3~4 문서 |
| 그 외 전 종목 | **수집하지 않음** | 0 |

전종목을 매일 수집하면 KIS 호출이 하루 3,981회(유량 제한상 200초 이상)인데 그중 99%는 쓰이지 않는다. 개인이 월 100건을 분석한다면 실제 데이터가 쌓이는 종목은 수십 개뿐이다.

**보유 종목도 시세를 따로 수집하지 않는다.** 다만 종합 판단(5단계)에서 포트폴리오 편중도를 참고하기 위해 **보유 현황(종목·비중)은 읽는다** — 앱이 이미 가진 데이터라 추가 수집이 없다.

### 일봉을 날짜별이 아니라 연도별로 묶는 이유

일봉은 항상 통째로 읽는 데이터라 날짜별로 쪼갤 이유가 없다.

| | 날짜별 1문서 | **연도별 배열 문서** |
|---|---|---|
| 3년치 조회 | 750 reads | **3 reads** |
| 종목당 문서 수 | 750개 | **3개** |

종목 1건 분석 시 Firestore 읽기는 일봉 3 + 재무 5~8 + 수급 1 + 종목정보 1 ≈ **12 reads**에 그친다.

### 캐시 신선도

재분석 시 캐시를 무조건 재사용하면 시세가 낡는다. 다음 기준으로 부분 갱신한다.

- **일봉·수급**: 마지막 저장일이 직전 거래일보다 오래됐으면 **부족한 구간만** 추가 조회
- **재무제표**: 분기보고서 제출 시점을 지났고 캐시에 해당 분기가 없으면 조회
- **뉴스**: 캐시하지 않고 매 분석마다 새로 조회 (분석의 핵심 변수)

**`analysis_requests` 문서 구조**
```js
{
  ticker, stockName,
  status: 'queued' | 'running' | 'done' | 'failed',
  progress: { step: 1~6, message: '재무제표 수집 중', pct: 30 },
  reportPath: 'stock_analyses/005930/reports/2026-08-05',
  priceAtAnalysis,          // 사후 검증용 — 필수
  error: null,
  createdAt, updatedAt
}
```

## 8. AI 모델 전략

| 용도 | 모델 | 이유 |
|---|---|---|
| 뉴스 분류·요약 | `claude-haiku-4-5` | 단순·대량 |
| 공시·사업보고서 해석 | `claude-sonnet-5` | 긴 문서 처리 |
| **종합 판단** | **`claude-opus-5`** | 제품의 본질. 아끼지 않는다 |
| 검증(팩트체크) | `claude-sonnet-5` | 대조 작업 |
| 일일 시황 브리핑 | `gemini-3.6-flash` (기존 유지) | 구글 검색 연동이 강점 |

**적용 기능**
- **Prompt Caching** — 분석 프레임워크 시스템 프롬프트를 캐싱. 종목마다 반복 호출하므로 비용 60~80% 절감. 캐시는 접두어 완전일치이므로 시스템 프롬프트에 날짜·종목명을 넣지 않는다.
- **Structured Outputs** (`output_config.format`) — 점수·등급·논거를 스키마로 강제. 기존 Gemini에서 겪은 JSON 파싱 실패(`responseMimeType` 충돌, 말줄임표 출력)가 구조적으로 발생하지 않는다.
- **Adaptive Thinking + effort** — 종합 판단 `high`, 뉴스 분류 `low`.
- **Batch API (50% 할인)** — Phase 4 전종목 야간 스크리닝.

**예상 비용:** 종목 1건 $0.15~0.4 (200~500원). 월 100건 분석 시 $15~40.

## 10. 단계별 계획 (Phasing)

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| **Phase 1** | 종목마스터 적재, API 클라이언트, **정량 분석 엔진(AI 없이)** | 종목코드 입력 시 전 지표가 계산돼 나온다 |
| **Phase 2** | Claude 파이프라인, 스코어링, 검증, 캐싱 최적화 | 리포트 JSON이 생성된다 |
| **Phase 3** | `/analysis` 화면, 실시간 진행률, 차트, 대시보드 뱃지 | 화면에서 분석을 요청하고 결과를 본다 |
| **Phase 4** | 전종목 야간 스크리너, 회고 검증, 가중치 튜닝 | 저평가 우량주 자동 발굴 |

**Phase 1을 AI 없이 먼저 끝내는 것이 중요하다.** 데이터 파이프라인이 부실하면 어떤 모델을 써도 결과가 쓰레기다.

## 12. 필요 시크릿

`web_app/.env.local`에 등록된 실제 변수명 기준이다(gitignore 확인 완료). 운영은 `defineSecret`으로 동일한 이름을 주입한다.

```
DART_API_KEY          DART OpenAPI
KIS_APP_KEY           한국투자증권 (실전투자)
KIS_APP_SECRET        한국투자증권 (실전투자)
ECOS_API_KEY          한국은행
NAVER_CLIENT_ID       NAVER API HUB → 헤더 X-NCP-APIGW-API-KEY-ID 로 전송
NAVER_CLIENT_SECRET   NAVER API HUB → 헤더 X-NCP-APIGW-API-KEY 로 전송
CLAUDE_API_KEY        Anthropic
```

**주의 2건**
- `NAVER_CLIENT_*`는 변수명만 구버전 관례를 따를 뿐, 실제로는 NCP 헤더(`X-NCP-APIGW-*`)로 보내야 한다. 엔드포인트도 `naverapihub.apigw.ntruss.com`이다.
- Anthropic SDK는 `ANTHROPIC_API_KEY`를 자동으로 읽지만 우리는 `CLAUDE_API_KEY`를 쓰므로, 클라이언트 생성 시 **키를 명시적으로 전달**해야 한다.
